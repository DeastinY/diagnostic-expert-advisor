What you get

Most of the work happens in the browser.

Import, checks, plots and datasets are part of the web app. Every step is also a command on the CLI and a function in Python, for scripts and for the cluster.

Guided data import

Throw in a folder of CSV files, Parquet tables, FHIR resources or a MIMIC-IV download. Layout, columns, time unit and units are recognized, the data is harmonized on the way in and stored efficiently. A guided import walks you through it.

Automated checks

Mixed units, values out of range, duplicates, numbers stored as text, timestamps before admission and differences between hospitals are reported before anything is written. Many findings come with a fix, and every fix is audited and stored with the cohort.

Show me

Plots without plotting

Clinical time series suggest the plots worth having, so they come out of the box: cohort overview, distributions per hospital, coverage and sampling grids, and a page per patient with the cohort median and IQR behind each signal. No code.

Show me

Harmonization across standards

Variables map to LOINC and UCUM codes, diagnoses are grouped across ICD-9 and ICD-10, drugs get RxNorm and ATC. Local naming goes into a mapping file, so every step is reproducible and explainable.

Show me

Datasets for research

The data in a machine-learning friendly (X, y) form: an encounter-level table with a prediction cutoff, a leakage guard and a split by encounter, patient or whole hospital. Build sub-cohorts and keep track of your experiments.

Show me

Optional AI advisor

Any OpenAI-compatible endpoint, local or hosted, suggests harmonization and processing steps from aggregates only, never from patient-level data. With MCP, local AI tools can be attached to the DEA; what grows out of that is open.

The five main views.

Screenshots of the app on a synthetic cohort from three hospitals, right after import. Click a screenshot to enlarge it.

Drop a folder, tick the fixes, then import.

Drop a MIMIC-IV download, FHIR resources or a table onto the page, or paste a path for a large folder that is already on the machine. The import shows what it recognized, runs the checks without writing anything, and opens with one line on how the data looks. The fixes come biggest first, the safe ones already ticked, the rest folded away for later.

  • Layout, columns, time unit and units are detected; you can correct them and add a separate static table
  • Mixed units are converted per row, °F to °C or mEq/L to mmol/L; rows in a unit that cannot be converted become their own variable
  • "Show the data" draws the variable behind a finding with its plausible range, so you decide on the picture
  • "Apply and check again" shows what remains in seconds; long imports show their stage while they run
  • Every fix is written to cohort.yaml; importing the same cohort again pre-ticks what you chose last time
# the same from the command line $ uv run dea import export.csv data/mine --fix recommended $ uv run dea check data/mine

What is left to fix stays in view, and local names get their codes.

The profile page carries the same findings list as the import, so the fixes you left for later are one tick away. A small dictionary matches English and German names, abbreviations and MIMIC item ids to 46 concepts with LOINC, UCUM, RxNorm and ATC codes. Names that denote another specimen or a drug level are left alone on purpose. Site-specific names go into a mapping file; the optional advisor proposes mappings for the rest, from aggregates only.

  • ICD-9 and ICD-10 diagnoses are grouped, so both versions end up in the same columns: dx_sepsis, dx_heart_failure, ...
  • Infusions and procedures are intervals, so "received norepinephrine" is a plain tag
  • FHIR R4 in and out, with the codes the dictionary knows
$ uv run dea suggest data/mine --apply $ uv run dea rename data/mine --mapping-file site.yaml

Pooling hospitals hides a lot.

Tell the DEA which static column names the site and it compares case mix, distributions, coverage and sampling per hospital. The findings try to tell a unit problem, which can be fixed for that site alone, from a device offset or a genuinely different population.

  • Hospital B charts temperature in °F; it is flagged and the fix only applies to B
  • Hospital C exports vitals every five minutes and has no lactate; both show up as coverage and sampling findings
  • The same overlay compares a selection with the rest of the cohort

One patient, with the cohort for context.

Each signal gets its own scale. The grey band is the hourly median and interquartile range of the cohort, so you see at a glance whether a value is unusual. Hovering aligns all panels in time.

  • Raw observations or a grid of your choice: 5 minutes, 15 minutes, hourly
  • Infusion rates, ventilation and procedures as spans on a rail
  • Ventilation modes, notes and other text as events

From a rule to a dataset.

Rules are SQL over the encounter-level feature table. Save them as filters or tags, split off sub-cohorts with their lineage recorded, and export a dataset whose features stop at the prediction cutoff.

  • The label can be a tag, a static condition or any rule over the whole stay
  • Columns that look like outcomes, the length of stay and the label itself are dropped
  • Split by encounter, by patient, or by holding out whole hospitals
$ uv run dea ml data/mimic ds.parquet \ --label "Severe ARDS" --cutoff 24 --split site
How it works

Under the hood it is one long table.

Observations, events and intervals are stored as Parquet, bucketed by encounter, and read lazily with Polars. Only what is needed gets loaded, which is why a MIMIC-sized cohort is not much slower to work with than a small one. Per-encounter code runs the same way on a laptop and on the SLURM cluster.

01 · import

Detect, convert, check

The source is scanned lazily, units are normalized per row and the checks run on a streaming pass plus a sample.

02 · store

Bucketed Parquet

Encounters are hashed into buckets and each file is sorted by encounter and time, so row-group statistics skip most of the data on a lookup.

03 · features

One row per encounter

Aggregates per variable, hours per intervention and the static columns. Filters and tags are SQL over this table, and results are cached.

04 · out

Frames, FHIR, reports

Polars or pandas frames, FHIR R4 resources, a standalone HTML report or a dataset for your model.

Get started

Install, start the server, drop your data in.

You need Python 3.11 or newer. We use uv for the environment, pip works as well. After dea serve everything else happens in the browser.

# install (or without a clone: uv tool install "dea[all] @ git+https://github.com/DeastinY/diagnostic-expert-advisor")
git clone https://github.com/DeastinY/diagnostic-expert-advisor.git dea
cd dea && uv sync --all-extras

# start the server, the demo cohort is one click away
uv run dea serve --data-dir data
→ http://127.0.0.1:8000
→ Add data → Demo gives you three synthetic hospitals
# start the server and drop the export onto the page
uv run dea serve --data-dir data
→ drop the folder onto the page → tick the fixes → Import
→ overview, distributions and patient pages are ready

# or do the same from the command line
uv run dea detect export.csv
uv run dea import export.csv data/mine --static patients.csv --fix recommended
uv run dea suggest data/mine --apply

  https://physionet.org/files/mimic-iv-demo/2.2/

→ stays, charts, labs, diagnoses, infusions, procedures

And in Python

cohort.py
from dea.io import load_cohort
from dea.ml import make_dataset

cohort = load_cohort("data/mimic")
cohort.features()                      # one row per encounter
cohort.filter('"lactate__max" > 2')    # any rule, any time

ds = make_dataset(cohort, label="Severe ARDS",
                  cutoff_hours=24, split="site")
X_train, y_train = ds.train()

Questions

A few things people ask.

Does any patient data leave my machine?

No. Everything runs locally. The optional AI advisor only gets a profile of the cohort, meaning aggregate statistics per variable, never encounter ids, timestamps or individual values. The web app shows you exactly what would be sent before you send it.

Do I have to write code?

No. Start the server, drop your data onto the page and you get the checks, the suggestions and all plots without a notebook. If you want to script things, the CLI and the Python API do the same.

How do I install and update it?

Either clone the repository and use uv run dea, or install it as a tool with uv tool install "dea[all] @ git+https://github.com/DeastinY/diagnostic-expert-advisor". dea update brings either one up to date, dea serve --auto-update does it before every start, and the app tells you in the sidebar when there is something new.

Is there help with getting started?

Yes. With the SDL Digital Patient at NHR4CES we run regular workshops, give demonstrations on your own data and help with the setup, from a laptop to the SLURM backend on the cluster. Write to richard.polzin@posteo.de.

How large can a cohort be?

The storage was built with MIMIC-sized cohorts in mind. On a synthetic cohort of 2,000 encounters and 54 million observations the feature table takes about three seconds and looking up a single encounter around 20 ms, with less than 2.5 GB of memory. The large gzipped MIMIC tables are converted to Parquet once and read lazily after that.

What does the data have to look like?

You need an encounter id, a time (timestamps or offsets since admission) and either variable/value columns or one column per variable. Non-numeric values become events. A separate table with static data is optional. MIMIC-IV folders and FHIR R4 resources are recognized as such.

Can I use it with several hospitals?

Yes. A static column that names the site turns on the per-site comparison: case mix, distributions, coverage, sampling and findings whose fixes only apply to one site. When building a dataset you can hold out whole hospitals as the test set.

What is the status?

Alpha. So far it has been tested on synthetic cohorts, on synthetic tables in the MIMIC-IV layout and on the SMART on FHIR sample data with 30+ organizations. Running it on a real ICU dataset and the SLURM backend on a real cluster are the next steps.
